# Enviro Grow fleet simulator

The repository includes a persistent CLI and daemon simulator for exercising the
local dashboard without physical boards. It generates protocol-compatible Grow
telemetry rather than emulating RP2040 hardware or executing MicroPython.

## Quick start

Start the dashboard and simulator in separate terminals:

```sh
task server
task sim
```

Then create and trigger a device from another terminal:

```sh
task sim:cli -- device create greenhouse \
  --dashboard-url http://127.0.0.1:5001 \
  --reading-frequency 15 --upload-frequency 1 --time-scale 60 \
  --auto-water
task sim:cli -- device trigger greenhouse
task sim:cli -- device list
```

Open <http://127.0.0.1:5001>. The simulated device appears exactly as a normal
Grow upload and can receive dashboard watering commands.

For background operation, use:

```sh
task sim:start
task sim:status
task sim:stop
```

State and logs live in `.enviro-simulator/`. Set `ENVIRO_SIM_STATE_DIR`,
`ENVIRO_SIM_HOST`, or `ENVIRO_SIM_PORT` before starting the daemon to override
the defaults. The control API binds to `127.0.0.1:8765` by default and has no
authentication; do not expose it on an untrusted network.

## Device commands

All management commands run through `task sim:cli -- ...`:

```text
device create NAME [options]       Create and call home for one device
device list                         List profiles and queue status
device show NAME_OR_UID             Show complete state
device update DEVICE --set K=V      Update profile fields
device delete DEVICE [--force]      Delete; queued data requires --force
device enable|disable DEVICE        Control scheduled readings
device online|offline DEVICE        Control simulated dashboard connectivity
device trigger DEVICE               Take a reading immediately
device override DEVICE K=V [...]    Hold one or more sensor values
device clear-override DEVICE [K...] Remove selected or all overrides
events [--device UID] [--limit N]   Inspect simulator activity
```

`--set` accepts JSON values and dotted paths. Examples:

```sh
# Change channel A's target and accelerate the clock.
task sim:cli -- device update greenhouse \
  --set moisture_targets.A=65 --set time_scale=120

# Hold channel A dry so automatic watering is exercised.
task sim:cli -- device override greenhouse moisture_a=20

# Simulate a dashboard outage. Readings continue into the persistent outbox.
task sim:cli -- device offline greenhouse
task sim:cli -- device trigger greenhouse
task sim:cli -- device online greenhouse
```

The background daemon log is available with:

```sh
task sim:cli -- daemon logs
```

## Fleet files

`fleet apply` creates missing profiles and updates matching profiles. Matching
uses `uid` when supplied, otherwise nickname. It never removes devices omitted
from the file. UIDs generated by fleet apply are deterministic from nicknames,
so applying the same document to a clean simulator produces the same identities.

```json
{
  "devices": [
    {
      "nickname": "grow-001",
      "dashboard_url": "http://127.0.0.1:5001",
      "reading_frequency": 15,
      "upload_frequency": 5,
      "time_scale": 60,
      "seed": 101,
      "auto_water": true,
      "moisture_targets": {"A": 55, "B": 60, "C": 50},
      "initial": {"moisture_a": 45, "moisture_b": 65, "moisture_c": 52}
    }
  ]
}
```

Apply it with:

```sh
task sim:cli -- fleet apply path/to/fleet.json
```

Every profile inherits omitted values from the defaults in
`enviro_simulator/settings.py`.

## Behavior model

Each device has a seeded, restart-safe state model:

- temperature and humidity follow bounded daily trends;
- pressure performs a small bounded random walk;
- luminance follows a day/night curve;
- each moisture channel dries at a slightly different rate;
- automatic watering runs when a reading is below its configured target;
- remote doses increase channel moisture and are validated against calibration
  and safety limits.

The model aims to be plausible and repeatable, not physically predictive.
Automatic watering adds five moisture percentage points per simulated pump
second. Remote watering adds 0.35 points per millilitre. Overrides are applied
before watering and remain active until cleared.

`time_scale=1` uses real time. At `60`, one wall-clock second advances one
simulated minute. Payload timestamps use simulated time. Manual triggers do not
alter the schedule.

## Upload and command fidelity

Readings are committed to SQLite before network delivery. A device starts an
upload when its queue reaches `upload_frequency`, sends oldest first, and keeps
failed readings for exponential retry. Queues survive daemon restarts.

A Grow watering command returned by `/api/readings` is executed once per command
ID. Results and pending acknowledgements are persisted. Failed acknowledgements
are retried after reconnect or daemon restart. Pump runtimes are recorded in
events but do not delay the daemon.

Provisioning call-home is best effort, matching the firmware: profile creation
succeeds if the dashboard is unavailable, and the failure is visible in device
status and events.

## Development and verification

```sh
task test       # all automated tests
task check      # compile and test
task sim:smoke  # 100-device generation/storage smoke benchmark
```

The smoke benchmark uses a temporary database and an in-process HTTP receiver,
so it does not require the dashboard or alter simulator state. It provisions 100
devices and runs three synchronized, persisted upload cycles. It validates local
simulator throughput rather than Flask dashboard capacity. Physical hardware
remains necessary for MicroPython and electrical validation.

## Known scope limits

- Enviro Indoor, Weather, and Urban are not supported in v1.
- The provisioning captive portal is tested separately by
  `tests/provisioning_preview.py`; it does not register daemon profiles.
- There is no simulator management UI in the dashboard.
- This is contract simulation, not instruction-level or hardware emulation.
